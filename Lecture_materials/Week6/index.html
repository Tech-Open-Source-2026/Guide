설치 전후

검사 도구의 설치

uv는 프로젝트의 Python 환경과 패키지 설치·실행을 관리한다. uv와 Python이 설치되어 있고, pyproject.toml이 있는 프로젝트 폴더에서 실행하는 예다.

설치할 도구를 기록

다른 버전의 검사 도구는 같은 코드를 다르게 판정할 수 있다. 다음 명령의 --dev는 검사 도구를 개발용 의존성으로 기록한다.
uv add --dev pytest mypy black flake8 flake8-bugbear pre-commit

무엇을 자동화하나

전: 각자 설치 명령과 버전을 기억한다. 후: pyproject.toml에 개발 의존성이 기록되고 uv.lock에 해결된 버전이 고정된다. uv run은 실행 전에 프로젝트 환경을 동기화한다.

예제로 보는 장점

  • 같은 버전으로 시작: 팀원이 같은 pyproject.toml과 uv.lock을 받으면, uv run black --version으로 기록된 Black 버전을 확인할 수 있다. 설치할 버전을 따로 전달할 필요가 줄어든다.
  • 업데이트 범위 선택: Black만 갱신하려면 uv lock --upgrade-package black을 실행한다. 전체 도구를 한꺼번에 올리지 않고, lock 파일의 변경과 포맷 결과를 검토한다. 호환성 때문에 관련 의존성도 바뀔 수 있다.

검사 대상의 차이

pytest에서 코드 품질 검사로

인사 함수의 요구사항은 문자열 이름을 받아 "Hello, 이름!"을 반환하는 것이다. pytest는 작성된 입력·기대값 사례를 실행하는 테스트 도구다.

테스트가 확인하는 사례

greet(name: str) -> str가 Hello, {name}!를 반환한다. uv run pytest -q는 greet("Hee")의 결과를 확인한다.

테스트 밖의 문제

greet(42)는 실행 결과가 그럴듯해도 타입 약속 위반이다. 작은따옴표 표기는 동작하지만 팀 표기가 달라진다. 사용하지 않는 import os는 불필요하다. mypy는 타입 위반, Black은 표기, flake8은 미사용 import를 각각 판정한다.

검사 명령의 실행

프로젝트 루트에는 pyproject.toml·uv.lock과 도구 설치 기록이 있다. src는 패키지 코드, tests는 테스트 폴더, example.py는 패키지 사용 예다.

프로젝트 루트에서 실행

uv run pytest -q
uv run mypy src tests example.py
uv run black --check src tests example.py
uv run flake8 src tests example.py

전과 후

uv run은 프로젝트 환경을 준비해 뒤의 명령을 실행한다. 네 줄은 각각 직접 실행해야 한다. pytest -q의 -q는 출력량을 줄인다. --check는 Black의 수정 필요 여부만 판정한다. 예: 테스트가 통과해도 example.py의 greet(42)는 문자열 인수를 요구하는 mypy 검사에서 실패할 수 있다.

서로 다른 질문

도구별 자동화 범위

greet(name: str) → str은 f"Hello, {name}!"를 반환한다. 테스트는 greet("Hee") == "Hello, Hee!" 한 사례만 확인하고, import os는 사용하지 않는다고 가정한다.

무엇을 검사하는가

pytest: 실제 결과 / mypy: 타입 약속 / Black: 코드 표기 / flake8·bugbear: 규칙 위반 / pre-commit: 커밋 시점의 자동 실행.

같은 코드의 서로 다른 상태

greet(42)는 greet("Hee") 테스트가 통과해도 mypy가 잡는다. import os는 반환값을 바꾸지 않아도 flake8이 잡는다. Black은 x=1을 x = 1로 고치지만 import os를 삭제하지 않는다. 파일 수정과 규칙 진단을 구분한다.

입력과 반환값

타입 힌트의 약속

타입 힌트는 함수가 받을 값과 돌려줄 값의 종류를 코드에 적는 표기다. 아래는 example.py의 전체 예이며, mypy는 코드를 실행하지 않고 그 약속을 검사한다.

처리 전

def greet(name: str) -> str:
    return f"Hello, {name}!"

print(greet(42))  # Hello, 42!
실행은 성공한다. 타입 힌트는 실행 중 인수를 차단하지 않는다.

처리 후

name: str은 문자열 입력, -> str은 문자열 반환 약속이다. mypy가 호출을 분석하면 정수 인수가 약속과 다름을 보고한다. 문자열 "42"로 고친다.

예제로 보는 장점

  • 목록의 원소도 검사: names: list[str] = ["Hee", 42]는 “문자열 목록” 약속을 어긴다. mypy가 42를 지적하고, "42"로 바꾸면 이 오류가 사라진다.
  • 함수 사용법 확인: greet(name: str) -> str만 읽어도 문자열을 넣고 문자열을 받는다고 알 수 있다. greet("Hee").upper()처럼 문자열 기능을 쓸 수 있지만, 정확한 인사 문구는 설명·테스트로 확인한다.

실행 전 오류 발견

mypy의 타입 검사

src의 greet(name: str) → str은 f"Hello, {name}!"를 반환한다. example.py는 이 함수를 import해 greet(42)를 호출하고, tests는 greet("Hee")만 확인한다.

왜 필요한가

테스트가 실행하지 않은 호출에도 타입 오류가 남을 수 있다. example.py의 greet(42)가 그 사례다.

자동 판정과 수정

uv run mypy src tests example.py
# 오류 요약: int 인수, str 필요
# 수정: greet("42")
# Success: no issues found
프로젝트 루트에서 실행한다. 출력은 핵심 문구만 발췌했다. mypy는 파일을 수정하지 않는다.

예제로 보는 장점

  • 함수 변경 후 호출부 찾기: greet의 입력 약속을 str에서 int로 바꾸면, 검사 대상의 greet("Hee")가 오류로 보고된다. 파일마다 호출을 눈으로 찾아다니는 일을 줄인다.
  • 빈 값 처리 누락 찾기: name: str | None은 문자열 또는 값 없음이다. 바로 name.upper()를 쓰면 mypy 오류다. if name is not None: 안에서 호출하면 이 오류가 사라진다.

두 도구의 보완 관계

타입 검사와 결과 검사

greet는 문자열 이름을 받아 "Hello, 이름!"을 반환해야 한다. 아래처럼 "Goodbye"를 반환하도록 잘못 고친 경우를 비교한다.

처리 전

def greet(name: str) -> str:
    return "Goodbye"
반환 타입은 str이므로 mypy는 통과한다. 그러나 greet("Hee")는 요구 결과와 다르다.

처리 후

uv run pytest -q는 Hello, Hee! 기대값과 실제 Goodbye를 비교해 실패한다. 반환문을 return f"Hello, {name}!"로 고치면 이 테스트도 통과한다. 타입과 기능을 각각 자동 검사한다.

예제로 보는 장점

  • 여러 입력을 다시 확인: 인사 함수의 테스트에 "" → "Hello, !", "희" → "Hello, 희!"를 추가한다. 함수를 바꾼 뒤 pytest를 한 번 실행하면 두 사례의 결과를 다시 확인한다.
  • 테스트 파일의 간섭 방지: pytest의 tmp_path는 테스트마다 별도 임시 폴더를 준다. A가 그 안에 result.txt를 만들어도 B의 폴더에는 없다. 파일 준비를 돕는 fixture를 쓰면 이전 테스트의 파일을 잘못 읽는 일을 줄인다.

설치 사용자에게 전달

배포 시 타입 정보

hello_open_source는 greet(name: str) → str을 제공하는 배포 패키지다. wheel은 설치용 묶음 파일이며, py.typed는 패키지에 타입 힌트가 들어 있음을 알리는 빈 표시 파일이다.

처리 전

개발자는 src의 타입 힌트를 검사할 수 있다. 그러나 사용자가 설치한 패키지에 py.typed가 없으면 mypy 기본 설정은 그 패키지를 타입 정보 없는 외부 라이브러리로 취급할 수 있다.

처리 후

src/hello_open_source/py.typed 빈 파일을 패키지에 포함한다. setuptools를 쓴다면 pyproject.toml에 아래 설정을 넣고 wheel을 다시 빌드한다.
[tool.setuptools.package-data]
hello_open_source = ["py.typed"]
설치 후 hello_open_source/py.typed가 있는지 확인한다.

예제로 보는 장점

  • 설치 사용자의 호출 검사: 설치된 hello_open_source가 greet(name: str) -> str 정보를 제공하면, 사용자 파일의 greet(42)도 mypy가 오류로 보고한다. 패키지 개발자만 타입 검사의 이익을 얻는 것이 아니다.
  • 반환값을 쓴 다음 줄 검사: 사용자가 message = greet("Hee") 다음에 message + 1을 쓰면 문자열과 정수를 더한 오류를 찾는다. message + "!"는 통과한다. 타입 표시는 실행 중 값을 차단하지 않는다.

표기 통일

Black의 자동 포맷

Black은 코드의 공백·따옴표·줄바꿈을 자동 정리하는 포매터다. src/hello_open_source/greeting.py의 greet(name: str) → str 함수 본문을 비교한다.

처리 전

return f'Hello, {name}!'
반환값은 맞지만 팀 코드의 따옴표 표기가 다르다.

처리 후

uv run black src/hello_open_source/greeting.py
# return f"Hello, {name}!"
Black이 파일을 직접 고친다. 자동화 대상은 공백·따옴표·줄바꿈 같은 표기다. 기능 결과는 pytest로 다시 확인한다.

예제로 보는 장점

  • 표기 지적을 줄이는 리뷰: 두 사람이 쓴 x=1과 x = 1이 모두 x = 1로 정리된다. 리뷰어가 “공백을 넣으세요”라는 수정을 반복해서 요청할 필요가 줄어든다.
  • 추가한 항목이 보이는 변경: 목록을 한 항목당 한 줄과 끝 쉼표로 정리하면, "Hee", 뒤에 "Kim",을 추가할 때 새 항목 한 줄만 변경 이력에 나타난다. 쉼표 때문에 기존 마지막 줄까지 고치는 일을 줄인다.

수정 필요 여부만 판정

Black의 검사 모드

프로젝트 루트에서 Black으로 src(패키지 코드), tests(테스트), example.py(사용 예)를 검사한다. 예를 들어 example.py에 x=1이 남아 있고 나머지 코드는 기준에 맞는 상태다.

처리 전

x=1은 실행되지만 Black 표기 기준에 맞지 않는다. 파일을 보존한 채 수정 필요 여부만 확인하려면 --check를 붙인다.

처리 후

uv run black --check src tests example.py
# 변경 필요: 종료 코드 1
uv run black src tests example.py
# 파일 수정
uv run black --check src tests example.py
# 변경 불필요: 종료 코드 0
--check는 파일을 바꾸지 않는다.

예제로 보는 장점

  • 누구의 편집기에서도 같은 판정: 동일한 Black 버전·설정을 쓴다면 A의 편집기가 남긴 x=1도 B의 터미널에서 --check로 검사할 때 종료 코드 1이다. x = 1로 고치면 0이 된다.
  • 실패 뒤 작업을 멈추는 조건: 자동 실행 절차를 “Black 종료 코드가 0일 때만 다음 단계 실행”으로 구성하면, x=1이 남은 제출은 다음 단계로 가지 않는다. --check 자체는 파일을 고치거나 배포를 중단시키지 않고 판정값을 준다.

불필요한 코드 검출

flake8의 코드 규칙

flake8은 코드 규칙 위반을 보고하는 린터다. src/hello_open_source/greeting.py에 아래 코드가 있고, 다른 파일에는 규칙 위반이 없다고 가정한다.

처리 전

import os


def greet(name: str) -> str:
    return f"Hello, {name}!"
os는 쓰지 않는다. pytest와 mypy는 이 문제를 판정하지 않는다.

처리 후

uv run flake8 src tests example.py
# F401: os imported but unused
첫 줄을 지우면 진단 없이 종료 코드 0이다. flake8은 진단을 자동화하며 기본 실행은 파일을 고치지 않는다.

예제로 보는 장점

  • 실행 전 이름 오타 발견: name = "Hee" 다음에 print(nmae)를 쓰면 F821이 정의되지 않은 이름을 보고한다. 프로그램을 실행해 그 줄에 도달하기 전에 오타를 찾는다.
  • 긴 분기 함수의 검토 대상 선정: 서로 독립된 if가 3개인 함수는 복잡도 4다. flake8 --max-complexity 3으로 검사하면 C901이 나온다. 기본 실행에는 없는 기준이며, 경고는 버그 확정이 아니라 함수를 나눌지 검토할 단서다.

공유 기본값 검출

bugbear의 추가 규칙

flake8-bugbear: flake8에 추가하는 오류·설계 실수 검사 규칙이다. 이름을 목록에 넣는 remember 함수에서, 이전 호출의 이름이 남는 공유 기본값 문제를 살펴본다.

처리 전 · 이전 호출의 값이 남음

def remember(name, names=[]):
    names.append(name)
    return names

remember("Hee") → ["Hee"]
remember("Kim") → ["Hee", "Kim"]

원인: 기본값 []는 함수 정의 때 한 번 생성된다. 두 호출이 같은 목록을 받고, append가 원본 목록에 이름을 추가해 이전 값이 남는다.

처리 후 · 호출마다 새 목록 생성

def remember(name, names=None):
    if names is None:
        names = []
    names.append(name)
    return names

remember("Hee") → ["Hee"]
remember("Kim") → ["Kim"]

B006은 공유 기본값 경고다. 수정 후에는 names를 생략한 호출마다 새 목록이 만들어진다.

예제로 보는 장점

  • 오래된 기본 시각 발견: def stamp(t=time.time()):의 기본값은 함수 정의 때의 시각이다. B008이 경고한다. 현재 시각이 필요하면 함수 본문에서 구한다.
  • 반복문 속 함수의 값 혼동 발견: funcs=[]에서 for i in range(3): funcs.append(lambda: i)를 실행한다. 나중에 각 함수를 호출하면 2, 2, 2다. B023이 같은 i 참조를 경고한다.

충돌 없는 설정

포매터와 린터의 기준

Black은 표기를 고치고 flake8은 규칙 위반을 알린다. 두 도구의 버전과 설정을 공유해 같은 코드를 서로 모순된 기준으로 판정하는 일을 줄인다.

두 파일의 줄 길이 설정

프로젝트 루트에서 각각 설정한다.

# pyproject.toml
[tool.black]
line-length = 88
# .flake8
[flake8]
max-line-length = 88

83자 코드 줄의 판정

Black이 포맷을 유지한 83자 줄을 가정한다. flake8 기본 제한 79자에서는 길이 경고 E501이 난다. 두 설정을 88자로 맞추면 이 줄의 길이 경고가 사라진다.

Black은 나눌 수 없는 긴 문자열을 88자보다 길게 남길 수도 있다. 같은 길이 설정이 모든 코드의 통과를 보장하지는 않는다.

예제로 보는 장점

  • 새 팀원의 기준도 일치: 88자 설정을 저장소에 넣으면 새 팀원도 같은 설정을 읽는다. 예를 들어 Black이 그대로 둔 83자 코드 줄이 flake8의 기본 79자 제한 때문에 실패하는 일을 줄인다.
  • 필요한 파일에만 예외 적용: .flake8의 [flake8] 아래에 per-file-ignores = src/hello_open_source/__init__.py:F401을 두면, 외부에 함수를 내보내는 파일만 미사용 import 예외로 삼는다. 다른 파일의 미사용 import는 계속 경고한다.

커밋 전 검사 지정

pre-commit의 공유 설정

hook은 특정 시점에 자동 실행할 작업이다. pre-commit은 Git 커밋 직전의 hook을 관리한다. stage는 git add로 다음 커밋에 넣기로 정한 파일 내용이다.

처리 전

개발자가 Black·flake8 명령을 잊고 커밋할 수 있다. 검사 명령을 반복 실행할 시점을 저장소에 기록한다.

처리 후

.pre-commit-config.yaml에 Black·flake8 hook과 버전을 기록한다. flake8 hook의 additional_dependencies에 flake8-bugbear를 추가해야 B006 같은 추가 규칙이 동작한다. 각자 uv run pre-commit install로 Git hook을 설치해야 커밋 직전에 실행된다. pytest·mypy는 별도 uv run으로 확인한다.

예제로 보는 장점

  • 추가한 검사만 자동 실행: JSON 문법 검사 hook인 check-json을 추가하면 {"name":}인 파일을 커밋할 때 실패한다. {"name":"Hee"}로 고치면 통과한다. Black·flake8 설정만으로 JSON 검사가 생기지는 않는다.
  • 변경한 Python 파일부터 검사: 추적 중인 Python 파일 100개 중 greeting.py만 stage에 올렸다면, 기본 Black hook은 그 1개를 받는다. 이 조건에서는 나머지 99개를 매 커밋마다 다시 포맷 검사하지 않는다.

설정에서 실행으로

로컬 hook 설치

Git 저장소 루트에 .pre-commit-config.yaml이 있고, Python hook인 Black·flake8의 버전이 지정되어 있다. pre-commit은 uv 개발 의존성으로 설치되어 있다.

처리 전

공유 설정 파일만 복사하면 각자의 .git/hooks/pre-commit은 생성되지 않는다. 커밋 때 자동 검사가 아직 없다.

처리 후

uv run pre-commit install
uv run pre-commit run --all-files
첫 명령이 로컬 Git hook을 연결한다. 두 번째의 --all-files는 Git 추적 파일 전체 중 hook 조건에 맞는 파일을 검사한다. Black이 수정하면 내용을 확인하고 재검사한다. 개발 의존성 환경과 hook의 격리 환경은 별개다.

예제로 보는 장점

  • 앱과 검사 도구의 설치 분리: Python hook인 Black은 pre-commit이 관리하는 별도 환경에 설치된다. 앱의 .venv에 Black을 직접 추가하지 않아도 hook을 실행할 수 있다. 단, pre-commit 자체는 실행 가능해야 한다.
  • 로컬 설치를 빠뜨린 변경도 검사: 기여자가 hook을 설치하지 않아 x=1을 커밋한 경우, 제출 때 검사하는 서버(CI)에 같은 설정과 pre-commit run --all-files을 연결하면 이를 발견한다. 서버 연결은 별도 설정이 필요하다.

작업 파일과 stage 확인

자동 수정 뒤 커밋

Git 저장소에 Black hook을 설치한 상태다. 작업 파일은 현재 편집 내용이고, stage는 git add로 다음 커밋에 넣기로 정한 내용이다.

처리 전

src/hello_open_source/greeting.py에 x=1을 쓰고 git add한 뒤 커밋하면 Black hook이 작업 파일을 고치고 커밋을 중단한다. 작업 파일은 x = 1, stage는 x=1인 상태다.

처리 후

git diff -- src/hello_open_source/greeting.py
git add src/hello_open_source/greeting.py
git commit -m "Unify greeting style"
git diff로 두 내용의 차이를 보고, git add로 수정본을 stage한다. 검사에 모두 통과하면 커밋이 생성된다. pre-commit은 검사·자동 수정을 실행하지만 수정본을 자동 stage하지 않는다.

문자열 이름을 인사 문자열로 바꾸는 greet 함수가 대상이다. 각 도구는 서로 다른 오류를 검사하므로 하나가 통과했다고 나머지가 통과한 것은 아니다.

uv: 도구 설치·프로젝트 환경 동기화. pre-commit: 커밋 직전 Black·flake8 실행. 개발자는 진단의 의미와 수정 내용을 확인하고, 네 검사를 다시 통과시킨 뒤 코드를 전달한다.
