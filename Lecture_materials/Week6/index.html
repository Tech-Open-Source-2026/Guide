설치 전후

검사 도구의 설치

왜 uv가 필요한가

사람마다 다른 도구 버전과 실행 환경을 쓰면 같은 코드에 다른 결과가 난다. 프로젝트 루트에서 개발 도구를 기록한다.

uv add --dev pytest mypy black flake8 flake8-bugbear pre-commit

무엇을 자동화하나

전: 각자 설치 명령과 버전을 기억한다. 후: pyproject.toml에 개발 의존성이 기록되고 uv.lock에 해결된 버전이 고정된다. uv run은 실행 전에 프로젝트 환경을 동기화한다.

장점

  • 환경 재현: 도구가 내부적으로 사용하는 라이브러리까지 버전을 기록해, 새 팀원도 기록된 의존성으로 시작한다.
  • 통제된 업데이트: 고정 버전을 유지하다가 특정 도구를 선택해 갱신하고, 검사 결과가 달라졌는지 확인할 수 있다.

입력과 반환값

타입 힌트의 약속

처리 전

def greet(name: str) -> str:
    return f"Hello, {name}!"

print(greet(42))  # Hello, 42!
실행은 성공한다. 타입 힌트는 실행 중 인수를 차단하지 않는다.

처리 후

name: str은 문자열 입력, -> str은 문자열 반환 약속이다. mypy가 호출을 분석하면 정수 인수가 약속과 다름을 보고한다. 문자열 "42"로 고친다.

장점

  • 자료구조의 약속: list[str]처럼 목록 안 원소의 타입까지 적어, 여러 단계로 전달되는 데이터 형태를 설명한다.
  • 협업 문서: 입력·반환 타입이 함수 선언에 남아, 호출자가 구현 전체를 읽기 전에 사용 방법을 파악한다.

실행 전 오류 발견

mypy의 타입 검사

왜 필요한가

테스트가 실행하지 않은 호출에도 타입 오류가 남을 수 있다. example.py의 greet(42)가 그 사례다.

자동 판정과 수정

uv run mypy src tests example.py
# error: Argument 1 has incompatible type "int"; expected "str"
# 수정: greet("42")
# Success: no issues found
mypy는 파일을 수정하지 않고 오류 위치를 알려 준다.

장점

  • 변경 영향 추적: 함수의 입력·반환 타입을 바꾸면, 검사 대상 여러 파일에서 맞지 않게 된 호출과 연산을 찾는다.
  • 조건 분기 검사: 값이 없을 수도 있는 str | None에서, None 확인 없이 문자열 기능을 쓰는 실수를 잡는다.

두 도구의 보완 관계

타입 검사와 결과 검사

처리 전

def greet(name: str) -> str:
    return "Goodbye"
반환 타입은 str이므로 mypy는 통과한다. 그러나 greet("Hee")는 요구 결과와 다르다.

처리 후

uv run pytest -q는 Hello, Hee! 기대값과 실제 Goodbye를 비교해 실패한다. 함수를 고치면 pytest도 통과한다. 타입과 기능을 각각 자동 검사한다.

장점

  • 경계값 반복 검증: pytest에 빈 이름·한글 이름 등 입력과 기대값을 묶어 주면, 같은 검사를 여러 사례에 반복한다.
  • 실행 상태 관리: 테스트 준비·정리를 재사용하는 fixture로 임시 파일이나 DB 연결을 관리해, 테스트 간 간섭을 줄인다.

표기 통일

Black의 자동 포맷

처리 전

return f'Hello, {name}!'
반환값은 맞지만 팀 코드의 따옴표 표기가 다르다.

처리 후

uv run black src/hello_open_source/greeting.py
# return f"Hello, {name}!"
Black이 파일을 직접 고친다. 자동화 대상은 공백·따옴표·줄바꿈 같은 표기다. 기능 결과는 pytest로 다시 확인한다.

  • 리뷰 집중: 여러 파일의 줄바꿈과 들여쓰기를 같은 규칙으로 맞춰, 리뷰에서 표기보다 동작 변경을 살핀다.

수정 필요 여부만 판정

Black의 검사 모드

처리 전

자동 검사 중 파일이 조용히 바뀌면 검토할 변경이 섞인다. 작은따옴표 버전은 Black 기준에 맞지 않는다.

처리 후

uv run black --check src tests example.py
# 변경 필요: 종료 코드 1
uv run black src tests example.py
# 파일 수정
uv run black --check src tests example.py
# 변경 불필요: 종료 코드 0
--check는 파일을 바꾸지 않는다.

장점

  • 서버에서도 같은 기준: 코드 제출 시 자동 검사하는 CI에 연결하면, 각자의 편집기 설정과 무관하게 표기 위반을 판정한다.
  • 후속 단계와 연결: 실패 종료 코드를 이용해 후속 배포 단계를 멈추도록 구성하고, 검사 중 원본 파일은 유지한다.

불필요한 코드 검출

flake8의 코드 규칙

처리 전

import os
def greet(name: str) -> str:
    return f"Hello, {name}!"
os는 쓰지 않는다. pytest와 mypy는 이 문제를 판정하지 않는다.

처리 후

uv run flake8 src tests example.py
# F401: os imported but unused
첫 줄을 지우면 진단 없이 종료 코드 0이다. flake8은 진단을 자동화하며 기본 실행은 파일을 고치지 않는다.

장점

  • 이름 오타 탐지: 정의하지 않은 변수 사용도 경고해, 해당 줄을 실행하기 전에 잘못된 이름을 찾는다.
  • 복잡한 함수 식별: 복잡도 제한을 별도로 설정하면, 분기가 많아 검토·테스트가 어려운 함수를 찾아 분리할 후보로 삼는다.

공유 기본값 검출

bugbear의 추가 규칙

위험의 의미: 실행 가능한 코드에서도 결과·상태가 의도와 달라질 수 있다는 뜻이다.
bugbear는 동작 오류·설계 실수의 패턴을 찾는다. 보안 취약점 검사를 대신하지 않는다.

처리 전 · 이전 호출의 값이 남음

def remember(name, names=[]):
    names.append(name)
    return names

remember("Hee") → ["Hee"]
remember("Kim") → ["Hee", "Kim"]

원인: def 실행 시 기본값 []는 한 번만 생성된다. names를 생략한 두 호출은 같은 리스트를 받는다. append가 그 리스트 자체를 수정하므로 첫 호출의 값이 다음 호출에도 남는다.

처리 후 · 호출마다 새 목록 생성

def remember(name, names=None):
    if names is None:
        names = []
    names.append(name)
    return names

remember("Hee") → ["Hee"]
remember("Kim") → ["Kim"]

B006은 공유 기본값을 경고한다. 수정 후에는 names를 생략할 때마다 함수 본문의 names = []가 실행되어 새 리스트를 만든다.

장점

  • 기본값의 계산 시점: 기본값에 현재 시각을 구하는 함수를 넣어, 호출마다 갱신될 것으로 오해하는 패턴도 경고한다(B008).
  • 반복문의 변수 참조: 반복문에서 만든 함수들이 나중에 같은 마지막 값을 읽을 수 있는 패턴을 경고한다(B023).

충돌 없는 설정

포매터와 린터의 기준

포매터 · 코드 표기 정리 도구: 공백·줄바꿈·따옴표를 정해진 형식으로 자동 수정한다.
예: Black은 x=1을 x = 1로 바꾼다.

린터 · 코드 규칙 검사 도구: 코드에서 규칙 위반이나 오류 가능성을 찾아 알린다.
예: flake8은 쓰지 않는 import os를 경고한다. 기본 실행은 파일을 수정하지 않는다.

처리 전

Black은 88자 줄을 허용하는데 flake8이 79자 초과를 보고하면 같은 줄에서 검사 기준이 충돌할 수 있다.

처리 후

pyproject.toml의 [tool.black] line-length = 88과 .flake8의 max-line-length = 88을 맞춘다. 83자 줄이 두 검사에서 통과한다. 설정은 검사 기준을 자동 적용한다.

장점

  • 팀 기준의 기록: 검사 기준을 파일로 공유하면, 새 팀원과 자동 검사 서버가 개인 설정에 의존하지 않고 같은 규칙을 읽는다.
  • 예외의 범위 제한: 특정 파일에 필요한 규칙 예외만 지정해, 예외 하나 때문에 프로젝트 전체의 검사를 끄는 일을 피한다.

커밋 전 검사 지정

pre-commit의 공유 설정

처리 전

개발자가 Black·flake8 명령을 잊고 커밋할 수 있다. 검사 명령을 반복 실행할 시점을 저장소에 기록한다.

처리 후

.pre-commit-config.yaml에 Black·flake8 hook과 버전을 기록한다. flake8 hook에는 bugbear를 추가한다. pre-commit이 커밋 직전 이 도구들을 자동 실행한다. pytest·mypy는 별도 uv run으로 확인한다.

장점

  • 검사 대상 확대: hook을 추가하면 Python뿐 아니라 YAML·JSON 문법이나 파일 끝 공백도 커밋 전에 검사할 수 있다.
  • 변경 파일 중심 실행: 기본적으로 커밋에 올린 파일 중 hook 조건에 맞는 파일을 골라, 매번 전체를 검사하는 부담을 줄인다.

설정에서 실행으로

로컬 hook 설치

처리 전

공유 설정 파일만 복사하면 각자의 .git/hooks/pre-commit은 생성되지 않는다. 커밋 때 자동 검사가 아직 없다.

처리 후

uv run pre-commit install
uv run pre-commit run --all-files
첫 명령이 로컬 Git hook을 연결한다. 두 번째는 추적 파일 전체를 미리 검사한다. 개발 의존성 환경과 hook의 격리 환경은 별개다.

장점

  • 도구 의존성 분리: Python hook은 별도 환경에 설치되어, 검사 도구의 의존성이 앱의 실행 환경과 섞이는 일을 줄인다.
  • 공유 서버 재검사: 같은 설정으로 CI에서 전체 파일을 검사하면, 로컬 hook을 설치하지 않은 기여자의 변경도 확인한다.

작업 파일과 stage 확인

자동 수정 뒤 커밋

처리 전

작은따옴표 코드를 git add한 뒤 커밋하면 Black hook이 작업 파일을 고치고 커밋을 중단한다. stage에는 이전 표기가 남는다.

처리 후

git diff -- src/hello_open_source/greeting.py
git add src/hello_open_source/greeting.py
git commit -m "Unify greeting style"
수정 내용을 보고 다시 stage한다. pre-commit은 검사·자동 수정을 실행하지만 수정본을 자동 stage하지 않는다.

동일한 도구 적용

한 파일 실습의 검사

처리 전

greet.py 한 파일에도 잘못된 호출, 들쭉날쭉한 따옴표, 미사용 import가 들어갈 수 있다. 패키지 구조가 없어도 문제는 같다.

처리 후

uv run pytest greet.py -q
uv run mypy greet.py
uv run black --check greet.py
uv run flake8 greet.py
검사 대상을 한 파일로 바꾼다. pytest는 명시한 파일의 테스트를 실행하고 나머지 도구는 같은 역할을 수행한다.

도구별 전후 변화

Summary

검사와 수정

pytest: 잘못된 실행 결과 → 실패 판정. mypy: 잘못된 타입 호출 → 오류 위치. Black: 다른 표기 → 통일된 파일. flake8·bugbear: 불필요하거나 위험한 패턴 → 규칙 진단.

자동 실행

uv: 도구 설치·프로젝트 환경 동기화. pre-commit: 커밋 직전 Black·flake8 실행. 개발자는 진단의 의미와 수정 내용을 확인하고, 네 검사를 다시 통과시킨 뒤 코드를 전달한다.
