5단계의 해결 · src/에서 Import 패키지 발견

이번 과제나이브한 시도해결·확인

두 줄은 어디에 쓰는가?

  • 둘 다 프로젝트 루트의 pyproject.toml 안에 쓴다.
  • [tool.setuptools.packages.find]는 Setuptools에게 Import 패키지를 찾으라는 TOML 표다.
  • where = ["src"]는 같은 표 안에서 루트 기준 검색 시작점 목록을 정한다.
# assignment-filename-checker/pyproject.toml
[tool.setuptools.packages.find]
where = ["src"]

설정이 실제 파일로 이어지는 과정

pyproject.toml의 where
        ↓
루트 아래 src/에서 검색
        ↓
src/assignment_filename_checker/ 발견
        ↓
wheel: assignment_filename_checker/
       checker.py  ✓
where는 패키지 이름이 아니라 그 상위 검색 출발점을 가리킨다.
파일 → TOML 표 → 값 → 발견 경로 → wheel 경로를 연결한다

7단계의 해결 · Build로 sdist와 wheel 생성

이번 과제나이브한 시도해결·확인

기본 빌드가 sdist를 거치는 이유

프로젝트 소스
   ↓ sdist 제작
.tar.gz를 임시로 풂
   ↓ 그 소스로 wheel 제작
.whl
  • python -m build의 기본 순서다.
  • sdist가 wheel을 다시 만들 만큼 완전한지도 시험한다.
  • --wheel이면 wheel만 직접 만들 수 있다.

“wheel은 바이너리”의 정확한 뜻

  • wheel은 다시 빌드하지 않고 설치 위치로 옮길 파일을 담은 built distribution이다.
  • 형식명이 모든 내용을 기계어로 컴파일했다는 뜻은 아니다.
  • 이 py3-none-any wheel은 순수 Python용이라 .py와 JSON을 담는다. 확장 모듈 wheel은 .so·.dll도 담을 수 있다.
호환 wheel만으로 설치 가능 · 일반 공개 배포는 sdist와 wheel을 함께 제공
이 수업은 설치 파일과 재빌드 가능한 소스 경로를 함께 검증한다

SUMMARY

Summary

문제를 발견하며 완성한 8단계

  • 데이터 누락에서 출발해 프로젝트 경계·세 이름·빌드 도구·메타데이터·코드 검색·JSON 포함을 결정했다.
  • 재빌드용 sdist와 설치 준비용 wheel을 만들었다.
  • 호환 wheel만으로 설치할 수 있지만 공개 배포에서는 보통 둘을 함께 제공한다.

최종 성공 기준

  • 순수 Python wheel에서 설치할 checker.py와 rules.json을 확인한다.
  • sdist에서 다시 빌드할 소스·설정·문서를 확인한다.
  • 각 형식의 메타데이터와 LICENSE까지 실제 내부 경로로 판정한다.
