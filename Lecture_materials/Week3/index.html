05 · FIGURE 3.1 · 교재 그림을 한글로 다시 읽기

Python 빌드 흐름

그림의 한글 해설

  1. 패키지 작성자가 build 같은 빌드 프런트엔드를 실행한다. 이 도구는 전역 또는 프로젝트 가상환경에 설치할 수 있다.
  2. 빌드 프런트엔드는 빌드 백엔드의 표준 hook을 호출해 패키지 산출물을 요청한다.
  3. pyproject.toml은 사용할 빌드 백엔드와 그 의존성을 지정한다.
  4. 소스 코드·빌드 설정·기타 메타데이터는 모두 백엔드의 입력이며 산출물 내용에 영향을 준다. 메타데이터의 위치·형식은 백엔드마다 다를 수 있다.
  5. build_sdist는 소스 배포 패키지 .tar.gz를, build_wheel은 설치용 wheel .whl을 만든다.
프런트엔드 사용자 인터페이스와 백엔드 제작 기능의 결합

06 · CONFIGURATION · backend는 실제로 호출되는 Python 모듈

pyproject.toml의 세 영역

[build-system]

빌드 도구 선언

build-backend = "setuptools.build_meta"로 backend 모듈을 정하고 필요한 Setuptools 버전을 선언한다.

빠지면: frontend가 어떤 모듈의 함수를 호출할지 알 수 없다.

[project]

배포 정보 선언

name·version·license로 만들 패키지의 정체성을 정한다.

빠지면: 파일명과 설치 조건을 만들 정보가 없다.

[tool.*] · 예: [tool.setuptools]

도구 전용 정책

Setuptools가 소스와 추가 데이터를 어디서 찾을지 정한다.

빠지면: 의도한 코드·데이터가 선택되지 않을 수 있다.

07 · FILE TREE · 배포판 구조와 messages.json 포함 확인

최소 프로젝트 구조

배포판의 전체 파일 구조

hello-open-source/
├── LICENSE
├── README.md
├── pyproject.toml
├── src/hello_open_source/
│   ├── __init__.py
│   ├── greeting.py
│   └── data/messages.json
└── tests/test_greeting.py

문서: LICENSE·README.md는 사용 조건·사용법을 전달한다.

설정: pyproject.toml은 빌드 도구·패키지 정보를 선언한다.

코드·검사: src/는 설치할 코드·데이터이고, tests/는 개발 중 검사하며 wheel에는 넣지 않는다.

messages.json은 무엇이며 어떻게 넣는가?

{"ko": "안녕하세요"} 같은 문구를 저장한다. greeting.py는 greet("ko") 실행 중 이 JSON을 열므로 설치된 wheel 안에도 있어야 한다.

[tool.setuptools.package-data]
hello_open_source = ["data/*.json"]

규칙의 뜻: hello_open_source 패키지의 data/ 아래 JSON을 배포물에 넣는다.

sdist 파일 목록 → src/hello_open_source/data/messages.json
wheel 파일 목록 → hello_open_source/data/messages.json

둘 다 필요한 이유: wheel은 설치 뒤 직접 읽는 파일을 담아야 하고, sdist는 기본 빌드에서 그 wheel을 다시 만드는 입력이므로 같은 JSON을 담아야 한다.

파일의 역할 → 포함 규칙 → sdist·wheel 내부 경로로 확인

08 · TOML · 선언별 이유와 산출물의 관찰 결과

최소 pyproject.toml

[build-system]
requires = ["setuptools>=77.0.3"] # 격리 환경에 설치
build-backend = "setuptools.build_meta" # 제작기

[project]
name = "hello-open-source" # 배포 이름
version = "0.1.0"          # 릴리스 식별
description = "A small greeting package"
readme = "README.md"       # 긴 설명 원본
requires-python = ">=3.10"
license = "MIT"
license-files = ["LICENSE"]
authors = [{ name = "Student Name" }]

선언이 만든 관찰 결과

name·versionhello_open_source-0.1.0-…whl
requires-pythonPython 3.9 설치를 pip가 거절
readmewheel METADATA의 긴 설명
license-fileswheel의 licenses/LICENSE

setuptools>=77.0.3은 이 예제의 SPDX·license-files 형식을 지원한다. 배포 이름 hello-open-source와 Import 이름 hello_open_source는 서로 다른 식별 공간이다.

09 · METADATA · 같은 정보를 읽는 세 소비자

메타데이터의 역할

사람

없으면: 설치 전 용도와 사용법을 알기 어렵다.

없으면: 실행할 수 없는 환경에도 설치될 수 있다.

없으면: 검색·버전 선택·업데이트 판단이 불가능하다.

한 선언이 사람·설치 도구·저장소의 다른 판단으로 이어진다

12 · LICENSE · 기계가 읽는 표현과 사람이 읽는 원문

라이선스 메타데이터

기계가 읽는 조건

[project]
license = "MIT"
license-files = ["LICENSE"]

METADATA에서 License-Expression: MIT를 확인한다.

표현이 없으면: 도구가 사용 조건을 자동 분류하기 어렵다.

사람이 읽는 원문

hello_open_source-0.1.0.dist-info/
└── licenses/LICENSE

wheel 목록에서 실제 MIT 원문 파일을 확인한다.

원문이 없으면: 사용자가 전체 법적 조건을 배포 파일만으로 확인할 수 없다.

SPDX 조건과 LICENSE 원문이 같은 사용 권리를 설명해야 한다

14 · SUMMARY

Summary

파일과 선언

코드·설정·문서는 역할이 다르며 pyproject.toml이 backend·이름·버전·정책을 연결한다.

도구와 산출물

frontend는 요청하고 backend는 제작한다. sdist는 소스 묶음, wheel은 설치 준비가 끝난 묶음이다.

첫 빌드 판정

python -m build 뒤 dist/의 두 파일에서 이름·버전·호환성 태그를 설명한다.

최종 설명: pyproject.toml → setuptools.build_meta → .tar.gz + .whl

파일 역할 → 빌드 역할 → 두 산출물
