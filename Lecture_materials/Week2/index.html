Git과 GitHub의 역할

로컬 기록과 원격 협업

같아 보이는 M의 위치가 상태를 구분한다

README.md만 선택하는 과정

status --short는 파일명 앞에 XY 두 칸을 쓴다. X는 스테이징, Y는 작업 디렉터리 상태다.

$ git status --short
 M README.md       # X=공백, Y=M
?? hello_open.py
$ git add README.md
$ git status --short
M  README.md       # X=M, Y=공백
?? hello_open.py
$ git commit -m "Document run command"
$ git status --short
?? hello_open.py

add 전후가 다른 이유

출력XY뜻
M README.md공백M수정했지만 아직 선택하지 않음
M README.mdM공백수정본을 스테이징함
README 행 없음공백공백커밋 뒤 세 위치가 같음
?? hello_open.py??add하지 않아 계속 미추적

핵심: 문자 M은 같지만 오른쪽 칸에서 왼쪽 칸으로 이동했으므로 같은 상태가 아니다.

두 Prefix의 실행 결과와 site-packages

코드별 실제 출력

>>> import sys
>>> print(sys.base_prefix)
/usr
>>> print(sys.prefix)
/home/student/open-source-week2/.venv
>>> print(sys.prefix != sys.base_prefix)
True

True는 현재 Python이 기준 설치가 아니라 프로젝트의 .venv를 사용한다는 뜻이다.

현재 Prefix가 설치 위치를 정한다

  • sys.base_prefix: 가상환경을 만든 기준 Python의 루트
  • sys.prefix: 현재 실행 환경의 루트
  • pip는 현재 루트 아래 lib/python3.12/site-packages/에 서드파티 패키지를 둔다.
.venv/
└─ lib/python3.12/site-packages/
   └─ requests/

따라서 프로젝트 A의 requests는 프로젝트 B의 설치 폴더를 덮어쓰지 않는다.

가상환경이 분리하는 것과 기록해야 할 것

학습 목표: 가상환경의 격리 범위를 구분하고, 다른 사람이 환경을 다시 만드는 데 필요한 기록을 선택한다.

분리되는 것과 분리되지 않는 것

  • 분리: Python 실행 경로와 서드파티 패키지 설치 폴더

  • 예: A의 requests 2.x는 B의 .venv에 영향을 주지 않지만 Windows와 Linux 경로 차이는 남는다.

저장소에 남길 재현 정보

  • 기록: Python 3.12, requirements.txt, 생성·설치·실행 명령
  • 제외: 컴퓨터마다 경로가 다른 .venv/ 디렉터리
  • 판정: 새 폴더에서 README만 따라 같은 출력을 만들 수 있어야 한다.

원격 연결의 -v·-M·-u

remote add origin URLGitHub 주소를 origin으로 등록

21 · SUMMARY

Summary

판단과 협업

  • 공개 상태는 사용 권리가 아니며 행동별 허용과 의무는 개별 라이선스로 판정한다.
  • Git은 로컬 이력을, GitHub는 Issue·Branch·Pull Request의 의도·격리·검토 증거 연결을 담당한다.
  • 설치 이름과 Import 이름은 다를 수 있고 PyPI는 배포물을, pip는 현재 환경 설치를 담당한다.

환경과 재현

  • 가상환경은 기준 Python과 환경별 설치 위치를 두 prefix로 나누고, PATH 맨 앞에 .venv/bin을 추가하면 짧은 python 명령이 환경 Python을 선택한다.
  • 실행 Python·pip·Import 파일이 같은 .venv를 가리킬 때 환경 일치를 증명할 수 있다.
  • .venv 대신 의존성·Python 버전·생성·설치·실행 절차를 기록하고 새 환경에서 다시 검증한다.
