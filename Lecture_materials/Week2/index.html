공개 상태와 오픈소스 권리

공개와 허가의 차이

  • 공개 저장소에서 코드를 볼 수 있다는 사실만으로 실행·수정·재배포 권리가 자동으로 생기지 않는다.

Git과 GitHub의 역할

로컬 기록과 원격 협업

  • Git은 전체 변경 이력을 로컬에 기록하므로 네트워크 없이도 커밋·Branch 비교·이력 탐색을 수행한다.

Issue·Branch·Pull Request의 증거 사슬

역할 분담

  • Issue는 문제와 완료 조건, Branch는 기본 흐름에서 격리한 작업, Pull Request는 차이·Review·자동 검사 결과를 맡는다.
  • 세 기록을 연결하면 문제 제기부터 병합까지 누가 무엇을 왜 판단했는지 추적할 수 있다.

무엇이 빠졌는가?

  • Issue와 Git 차이가 남아도 Review 대화와 자동 검사 승인 결과가 삭제되면 병합 판단 근거를 복구하기 어렵다.
  • 기본 Branch를 안전하게 유지하려면 완료 조건과 연결된 변경만 필수 Review와 검사를 통과한 뒤 병합한다.

Python 패키지의 두 이름과 배포

Import와 Distribution

  • Import package는 Python 코드가 import my_tool로 찾는 모듈 경계이고, Distribution package는 pip install my-tool로 설치하는 배포 산출물이다.
  • 두 이름은 같을 수도 다를 수도 있으므로 설치 이름과 Import 이름을 각각 확인한다.
  • 단순 ZIP을 Distribution package로 만들려면 빌드 설정과 이름·버전·Python 요구사항 같은 메타데이터가 필요하다.

PyPI와 pip

  • PyPI는 버전별 배포 파일과 메타데이터를 호스팅하고 pip는 호환 배포 파일을 현재 Python 환경에 설치한다.
  • .venv나 다른 컴퓨터의 전체 site-packages를 복사하는 방식은 배포 규격이 아니며 이식성을 낮춘다.

좋은 패키지 경계

분리 기준

  • 응집도는 함께 변하는 기능을 모으고, 캡슐화는 내부 구현을 공개 API 뒤에 숨긴다.
  • 소유권과 변경 이유가 독립적이고 공개 API·테스트·배포 시점도 따로 운영될 때 분리 근거가 강하다.
  • 함수 수·파일 수·코드 줄 수만으로는 안정적인 경계를 판단할 수 없다.

결합 비용

  • 경계를 나누면 한 영역의 변경이 다른 영역의 내부 구현까지 요구하지 않도록 결합을 줄여야 한다.
  • 분리 뒤에도 항상 함께 수정·테스트·배포한다면 경계가 운영 비용만 늘리는지 다시 점검한다.

가상환경의 두 Prefix

기준과 현재 환경

  • 기준 Python 설치는 sys.base_prefix, 현재 가상환경 디렉터리는 sys.prefix가 가리킨다.
  • 가상환경에서는 두 값이 다르고, 가상환경이 아니면 일반적으로 두 값이 같다.
import sys
print(sys.base_prefix)
print(sys.prefix)
print(sys.prefix != sys.base_prefix)  # 가상환경이면 True

공유와 격리

  • 표준 라이브러리는 기준 설치를 공유하고 서드파티 패키지는 가상환경의 site-packages에 설치한다.
  • 이 분리는 프로젝트 A의 패키지 버전이 프로젝트 B의 설치 위치를 덮어쓰지 않게 한다.

활성화와 정확한 설치 대상

활성화의 직접 효과

  • source .venv/bin/activate는 .venv/bin을 셸의 PATH 앞에 두어 짧은 python 명령이 환경 Python을 고르게 한다.
  • 활성화는 pyvenv.cfg를 다시 쓰거나 기준 Python의 패키지를 복사하지 않는다.

활성화 없이 고정하기

  • .venv/bin/python -m pip install requests는 앞에 적은 환경 Python의 pip를 실행하므로 설치 대상을 .venv로 고정한다.
  • pip show는 정보 조회, --dry-run은 설치 계획 확인이므로 실제 설치 완료 명령과 구분한다.

실행·설치·Import 경로의 일치

세 경로

  • sys.executable은 실행 Python, python -m pip --version은 설치 도구, requests.__file__은 실제 Import 파일의 위치를 보여 준다.
  • 세 결과가 모두 프로젝트 A의 .venv 아래를 가리켜야 실행·설치·Import가 같은 환경에 묶였다고 판정한다.
.venv/bin/python -c "import sys; print(sys.executable)"
.venv/bin/python -m pip --version
.venv/bin/python -c "import requests; print(requests.__file__)"

가상환경의 범위와 한계

여러 Python과 여러 프로젝트

  • Python 3.11과 3.12 같은 기준 설치를 따로 두고 각 프로젝트가 필요한 버전으로 자체 .venv를 만들 수 있다.
  • 가상환경은 Python과 패키지 설치 위치를 분리하지만 운영체제·CPU·외부 서비스까지 복제하지 않는다.

재현을 위한 기록

  • 저장소에는 .venv 자체가 아니라 Python 요구 버전, 의존성 목록, 생성·설치·실행 명령을 기록한다.
  • 환경이 이상하면 활성화 표시보다 실제 Python·pip·Import 경로를 먼저 확인한다.
